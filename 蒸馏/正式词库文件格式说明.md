# Recall 正式词库文件格式说明

## 1. 文档目的

本文档定义 Recall App 正式词库的最终交付格式、字段含义、数据清洗规则和验收标准。

无论原始数据来自 Excel、CSV、PDF、网页或其他资料，蒸馏完成后都必须转换为本文档规定的 JSON 文件。该 JSON 将作为 App 内置词库导入 SQLite。

第一版建议只制作一个词库：

```text
考研英语词库
```

词库具体数量以最终清洗后的有效单词数为准，不要为了凑“5500”而添加重复、错误或低质量数据。

---

## 2. 最终交付文件

推荐文件名：

```text
kaoyan_v1.json
```

文件必须满足：

- 编码：UTF-8，不带 BOM。
- 内容：标准 JSON，不能包含注释。
- 根节点：一个 JSON 对象。
- 最终只交付一个完整文件，不使用 Markdown 代码块包裹。
- JSON 中不能有尾随逗号。
- 中文、IPA 音标和英文标点必须能够正常显示。

---

## 3. 完整 JSON 结构

```json
{
  "schemaVersion": 1,
  "book": {
    "id": "kaoyan_v1",
    "name": "考研英语",
    "version": 1,
    "description": "考研英语核心词汇",
    "expectedWordCount": 2,
    "source": "填写词库原始资料来源",
    "licenseNote": "填写授权、许可或使用范围说明"
  },
  "words": [
    {
      "id": "abandon",
      "position": 1,
      "word": "abandon",
      "phonetic": "/əˈbændən/",
      "meaning": "v. 放弃；抛弃",
      "example": "They had to abandon the old plan."
    },
    {
      "id": "ability",
      "position": 2,
      "word": "ability",
      "phonetic": "/əˈbɪləti/",
      "meaning": "n. 能力；才能",
      "example": "She has the ability to solve complex problems."
    }
  ]
}
```

`expectedWordCount` 必须等于 `words` 数组中实际记录数量。上例只有两条数据，所以填写 `2`；正式词库应填写最终实际数量。

---

## 4. 词库元数据字段

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `schemaVersion` | 整数 | 是 | 当前固定为 `1` |
| `book.id` | 字符串 | 是 | 当前固定为 `kaoyan_v1` |
| `book.name` | 字符串 | 是 | 当前填写 `考研英语` |
| `book.version` | 整数 | 是 | 第一版为 `1`，后续数据更新时递增 |
| `book.description` | 字符串 | 是 | 简洁说明词库用途和范围 |
| `book.expectedWordCount` | 整数 | 是 | 必须等于实际单词记录数量 |
| `book.source` | 字符串 | 是 | 说明原始词表、词典或资料来源 |
| `book.licenseNote` | 字符串 | 是 | 说明数据授权、许可或允许的使用范围 |
| `words` | 数组 | 是 | 保存全部单词，不能为空 |

不确定数据授权时，必须如实记录并在正式发布前人工确认，不能编造授权信息。

---

## 5. 单词记录字段

每个单词对象只能使用以下字段：

```text
id
position
word
phonetic
meaning
example
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | 字符串 | 是 | 单词的稳定唯一标识 |
| `position` | 整数 | 是 | 单词在词库中的学习顺序，从 1 开始 |
| `word` | 字符串 | 是 | 英文单词或固定词组 |
| `phonetic` | 字符串 | 是 | Unicode IPA 音标 |
| `meaning` | 字符串 | 是 | 中文释义，建议包含词性 |
| `example` | 字符串 | 是 | 自然、完整、可理解的英文例句 |

不能输出额外字段，例如 `difficulty`、`frequency`、`memoryLevel`、`reviewDate` 等。这些属于用户学习数据或未来功能，不属于基础词库。

---

## 6. `id` 生成规则

`id` 必须等于 `word` 去除首尾空格并转换为小写后的结果。

示例：

| `word` | 正确的 `id` |
| --- | --- |
| `Abandon` | `abandon` |
| `Take off` | `take off` |
| `Well-being` | `well-being` |
| `Don't` | `don't` |

规则：

- 不使用随机 UUID。
- 不使用中文释义作为 ID。
- 不使用序号作为 ID。
- 保留单词内部的空格、连字符和撇号。
- 同一个英文拼写只能出现一次。
- 大小写不同但拼写相同的记录视为重复。

当前 App 已经使用规范化单词作为学习记录 ID，遵守该规则可以保留已有学习和复习历史。

---

## 7. `position` 排序规则

`position` 决定 App 分配新词的顺序。

必须满足：

- 第一条记录为 `1`。
- 后续记录依次为 `2、3、4……N`。
- 不能重复。
- 不能为零或负数。
- 不能跳号。
- `words` 数组本身也应按照 `position` 升序排列。

如果原始词表已有官方顺序，应保留官方顺序；如果没有，建议按照原始资料顺序或明确、稳定的排序规则生成，不要每次随机排列。

---

## 8. `word` 内容规则

- 去除首尾空格。
- 使用正常英文拼写。
- 普通单词原则上使用小写形式。
- 专有名词确实需要大写时可以保留，但 `id` 仍使用小写。
- 固定搭配或词组可以包含空格。
- 不在 `word` 中添加词性、中文释义、音标或序号。
- 不把同一个单词的不同释义拆成多条重复记录。

正确：

```json
"word": "abandon"
```

错误：

```json
"word": "abandon v. 放弃"
```

---

## 9. `phonetic` 音标规则

- 必须使用 Unicode IPA，不能使用乱码或图片。
- 建议使用 `/.../` 包裹。
- 音标必须与单词对应。
- 如果英式和美式发音明显不同，可以写在同一个字符串中。
- 不允许使用空字符串、`unknown`、`暂无` 等占位内容。

单音标示例：

```json
"phonetic": "/əˈbændən/"
```

英美音标示例：

```json
"phonetic": "UK /ˈrekɔːd/; US /ˈrekərd/"
```

如果无法从可靠资料确定音标，应加入单独的问题清单等待人工核对，不能凭空生成一个看似合理的音标。

---

## 10. `meaning` 释义规则

- 使用简体中文。
- 建议保留常用词性，例如 `n.`、`v.`、`adj.`、`adv.`。
- 优先保留考研中常见、重要的释义。
- 多个释义使用中文分号 `；` 分隔。
- 保持简洁，避免复制整段词典解释。
- 同一单词的多个词性和核心释义合并到一条记录。
- 不填写助记法、同义词扩展、复习建议或难度判断。

示例：

```json
"meaning": "n. 记录；纪录；v. 记录，录制"
```

不推荐：

```json
"meaning": "这个词非常重要，考研经常考，大家一定要记住……"
```

---

## 11. `example` 例句规则

例句用于第一层学习和暂时的离线语境强化，质量非常重要。

必须满足：

- 是完整、自然、语法正确的英文句子。
- 建议长度为 6～20 个英文单词。
- 必须包含目标单词或它的正常词形变化。
- 应能帮助理解该记录中的核心释义。
- 不包含中文翻译。
- 不包含 Markdown、HTML 或特殊标记。
- 不使用过度复杂、晦涩或需要大量背景知识的句子。
- 不同单词尽量不要重复使用完全相同的例句。
- 不要用无意义模板机械拼接，例如 `I like abandon very much.`。

正确示例：

```json
"example": "They had to abandon the old plan."
```

如果使用词形变化也可以：

```json
{
  "word": "generate",
  "example": "The new system generates a report every morning."
}
```

---

## 12. 重复词和多义词处理

### 12.1 同一拼写、多个释义

合并为一条记录：

```json
{
  "id": "record",
  "position": 125,
  "word": "record",
  "phonetic": "/ˈrekɔːd; rɪˈkɔːd/",
  "meaning": "n. 记录；纪录；v. 记录，录制",
  "example": "The system records every review result."
}
```

### 12.2 大小写不同

`Abandon` 和 `abandon` 视为同一个单词，不能分别保留。

### 12.3 完全相同的记录

只保留一条，并重新整理后续 `position`，保证连续。

### 12.4 不同单词形式

如果原始考研词表把不同形式列为独立词条，可以分别保留，例如 `economy`、`economic`、`economical`；但不要由 AI 无限制扩展原始词表中不存在的派生词。

---

## 13. 禁止行为

蒸馏过程中禁止：

- 为了凑数量而添加原始词表中不存在的词。
- 伪造数据来源或授权信息。
- 在没有可靠依据时编造 IPA 音标。
- 输出重复单词。
- 用随机顺序替代原始顺序。
- 把多个单词塞进一个 `word` 字段。
- 把单词的多个释义拆成重复词条。
- 输出空释义、空音标或空例句。
- 使用 `TBD`、`unknown`、`暂无`、`待补充` 等占位值。
- 把 Markdown 代码块标记写入最终 JSON。
- 修改 JSON 字段名或大小写。
- 添加用户记忆状态、复习间隔或难度评分。

遇到不确定的数据时，应单独生成问题清单交给人工审核，不能把猜测混入正式词库。

---

## 14. 大词库分批蒸馏规则

完整词库可能有数千条，AI 可以分批处理，但必须遵守：

1. 先锁定一份完整的原始词表和全局顺序。
2. 每批建议处理 100～200 条。
3. 每批使用全局 `position`，不能从 1 重新编号。
4. 每批完成后立即检查重复 ID、缺失字段和位置范围。
5. 全部批次完成后合并为一个 `kaoyan_v1.json`。
6. 合并后执行一次全量去重和连续性检查。
7. 最终 `expectedWordCount` 填写合并清洗后的实际数量。

中间批次可以暂存为 JSON 数组，但最终文件必须符合第 3 节规定的完整结构。

---

## 15. 最终验收清单

交付前必须逐项检查：

- [ ] 文件可以被标准 JSON 解析器正常解析。
- [ ] 文件编码为 UTF-8 且不带 BOM。
- [ ] `schemaVersion` 等于 `1`。
- [ ] `book.id` 等于 `kaoyan_v1`。
- [ ] `book.version` 等于当前词库版本。
- [ ] `expectedWordCount` 等于 `words.length`。
- [ ] 所有 `id` 唯一。
- [ ] 所有 `word` 忽略大小写后唯一。
- [ ] 每个 `id` 都等于对应 `word` 去除首尾空格后的小写形式。
- [ ] 所有 `position` 唯一且从 1 连续到 N。
- [ ] `words` 数组按照 `position` 升序排列。
- [ ] 每条记录只包含六个规定字段。
- [ ] 每条记录的六个字段都存在。
- [ ] `id`、`word`、`phonetic`、`meaning`、`example` 都不是空字符串。
- [ ] 每个 `position` 都是正整数。
- [ ] IPA 音标没有乱码。
- [ ] 中文释义没有乱码。
- [ ] 英文例句语法正确且与目标词义相关。
- [ ] 例句包含目标词或其正常词形变化。
- [ ] 没有占位值和待补充内容。
- [ ] 没有混入用户学习状态或复习数据。
- [ ] 数据来源和授权说明真实、可核查。

只有全部检查通过的文件才能导入 Recall App。

---

## 16. 可直接交给其他 AI 的任务指令

可以将本文档连同原始词表一起提供给负责蒸馏的 AI，并使用以下指令：

```text
请根据《Recall 正式词库文件格式说明》处理我提供的原始考研英语词表。

你的任务是清洗和结构化已有词表，不是自由扩充词库。必须保留原始词表范围和稳定顺序，为每个单词补齐可靠的音标、简体中文核心释义和自然英文例句。

严格遵守文档中的字段、ID、排序、去重、音标、释义和例句规则。遇到无法可靠确认的数据时，不要猜测或伪造；将其记录到单独的问题清单中等待人工审核。

如果数据量过大，可以每批处理 100～200 条，但必须使用全局 position。全部完成后合并为一个 UTF-8、无 BOM、可被标准解析器解析的 kaoyan_v1.json，并按照文档中的验收清单执行全量检查。

最终交付：
1. kaoyan_v1.json
2. 数据校验报告.md
3. 待人工确认问题.md（没有问题时也要明确写“无”）
```
